## 2. Findings

**R1: BLOCK.** Where: design Decision 8, "Rollback" step 1 and "Deployment" step 1; D23.
- **Claim:** On MySQL, the old code cannot start against a migrated `pets` table. The old `data.sql` inserts pets by position with 5 values, the migrated table has 6 columns, and init runs on every start with no `continue-on-error`. So "redeploy the old code" (rollback) fails, and so does any restart of old instances between step 1 and step 2. Postgres is not affected.
- **Evidence:**
  - VERIFIED: `db/mysql/data.sql:36` `INSERT IGNORE INTO pets VALUES (1, 'Leo', '2000-09-07', 1, 1);`
  - VERIFIED: `application-mysql.properties:7` `spring.sql.init.mode=always`. No `spring.sql.init.continue-on-error` in that file or in `application.properties`.
  - VERIFIED: design:114 says "The old code keeps working against the new table because it never names the column".
  - VERIFIED: Postgres's old `data.sql` names its columns (`db/postgres/data.sql:36`).
  - INFERRED, not run: MySQL raises error 1136, "Column count doesn't match value count", and `IGNORE` does not suppress it. That would make startup fail.
- **Falsification:** This finding is wrong if MySQL 9.7 accepts a 5-value positional `INSERT IGNORE` into a 6-column table, or if something else sets `continue-on-error=true`.
- **Confidence:** medium-high.
