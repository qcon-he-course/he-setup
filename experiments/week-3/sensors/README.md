# Week 3 sensors

Deterministic checks that run before any model reviews a change (step 5), and whose results the reviewers receive. Each works on the working tree against a base commit (default `HEAD`, untracked files included) or on a commit range `base head`. Each has a test script; run it after any change.

| Sensor | What it reports | Exit | Tests |
|---|---|---|---|
| `risk-floor.py [--tier] [base [head]]` | The change's lowest possible risk tier (mechanical, bounded, material, critical) and what triggered it: paths, added lines, new `pom.xml` dependencies and plugins. A model may raise the tier; nothing lowers it | 0 | `risk-floor.test.sh` (17) |
| `test-delta.py [base [head]]` | Deleted tests, renamed tests (same body under a new name), removed assertions (moved lines excepted), skips, broad catches, changed protected checks, test configuration in the build file | 0 nothing, 1 findings | `test-delta.test.sh` (23) |
| `glossary-check.sh [base]` | Words `GLOSSARY.md` says to avoid, in added lines | 0 nothing, 1 findings | `glossary-check.test.sh` (12) |
| `protected-paths.py [--approvals FILE] <clone>` | The clone's tracked files that the `protected-check` rules cover, minus those a person approved a change to. demo.sh mounts them read-only for the coding agent (e17) | 0 | Checked against `week-3-start` and the first e17 approval, 1 November |
| `scenario-coverage.py [--manual FILE] <clone> [report dirs...]` | Whether each scenario in the change's spec deltas is shown by a test at its declared level (`- **CHECKED AT** unit/form/database/mysql-postgres/concurrency/manual`). A test shows a scenario by its name (the title in lowerCamelCase, extra words allowed, longest match wins); its level comes from its class's annotations; ran and passed from the Surefire reports. PRESENT, ABOVE (tested higher than needed, informational), FAILED, UNTESTED, NO LEVEL; and the pyramid's shape. Presence is not adequacy | 0 every scenario present or above, 1 findings | `scenario-coverage.test.sh` (23) |
| `known-defects.py check <list> <ticket dir>` | Checks `baseline/known-defect-tests.txt` before step 5 uses it: each line `<test class>#<method> <ticket>`, and each ticket a file whose `**Status:**` says open. A closed or missing ticket fails the check and demo.sh stops, so the list cannot hide a failure. The list sits here, outside the clone, so the coding agent never sees it; a team that commits it to its repository adds it to the protected checks in `risk-rules.txt` | 0 valid, 1 a bad entry | `known-defects.test.sh` (8) |
| `step5.sh <clone> <out>` | All of step 5 on a change, cheapest first: the three sensors above, the architecture rule, the build's own checks, `./mvnw validate` (B1's formatter and nohttp checkstyle, the enforcer's Java version, and anything else the pom binds to `validate`; on a failure the formatter and nohttp also run on their own, since `validate` stops at the first, so each problem is reported with its file and line; a failure makes the change not eligible, as `./mvnw verify` would fail), the full suite without the known-defect tests, the known-defect lane (those tests run on their own with their whole class, `KNOWN_DEFECT_RUNS` times, default 3; shown, not counted) and PIT, summarised in `<out>/sensors.md`. The suite's and PIT's reports are deleted before each runs, so a build that fails before its tests leaves no results (e22's F3 read the previous case's reports) (survivors marked when they sit on lines the change adds). Run by `demo.sh e18` | 0 | Run on e17's change in the cloud workspace, 1 November: 2 min 12 s |
| `triage.py prepare <inputs>` / `check <inputs> <reply> [clone]` | Step 7's policy. `prepare` lists every finding in the reviews and the test-delta audit; `check` audits the clerk's merge (each source once, none invented, no disposition lowered, no sensor finding or substantial finding set aside without a reason), computes eligibility (no open BLOCK, and no failing test in the suite or in the host's MySQL and Postgres run, in either order) and the sign-off from the floor, counts doubt theater, and writes `packet.md`. Classes that passed on the host in every order leave the "Not run" row. It reads a finding from a bold line or a heading that starts with its id, in the review's Findings section, with the disposition on that line, on a Disposition line or leading its first lines. It fails closed: a finding with no readable disposition, or a review with none it can read, fails the audit, and a packet that fails its audit is not eligible (e22: the old parser lost 7 of 28) The packet's "Merges without a person" row is step 8b's rung: yes only for a bounded-or-lower floor, an eligible packet, no question, no fix going back to the author, and nothing unrun or unverified | 0 written, 1 audit failed | `triage.test.sh` (51) |
| `step5-docker.sh <clone> <out>` | The `MySql*Tests` and `Postgres*Tests` classes, run twice in opposite class orders with `./mvnw` on the presenter's machine, where Docker is (no agent container has a Docker socket). Appends a section to `sensors.md`. With colima it sets `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE`. Run by `demo.sh e18` after `step5.sh`; `W3_DOCKER_TESTS=0` skips it | 0 | First run 1 November (one order): all six Docker tests pass, 34 s |
| `freeze-probe.sh [clone]` | Whether the frozen architecture rule catches one more `rejectValue` call in `PetController`, on a throwaway copy. Run by `demo.sh e15` before the review | 0 | Checked by hand, 31 October |

`risk-rules.txt` holds the rules for the three Python tools: which paths and patterns give which tier, and which files are protected checks. It lives here, in the harness, so a change to PetClinic cannot edit the rules that classify it. The tiers follow the reference document, section 4.2.
