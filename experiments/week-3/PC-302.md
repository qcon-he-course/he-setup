# PC-302: Two pets added to one owner at the same moment can lose one

**Status:** open

**Type:** defect, existing since before PC-301 (present at `week-3-start`, 76adfc4). Found 1 November by the coding agent in e17 while running the existing race test; confirmed by probe runs the same day.

## What happens

Two requests add a pet to the same owner at the same moment. Both succeed. Afterwards the owner has only one new pet: the other is still in `pets` but with `owner_id` set to null, so it no longer appears on the owner's page.

The same race lets two pets with the same name be added to one owner: the unique constraint `unique_owner_pet_name` never fires, because the first pet has already been detached when the second is saved.

## Why (from the e17 agent's SQL log; INFERRED, not yet confirmed in code)

The second request loads the owner, and its pet list, before the first request commits. Saving that owner with `saveAndFlush` merges a pet list that lacks the first request's pet, and Hibernate writes `update pets set owner_id=null where owner_id=? and id=?` for it.

The defect predates the course and predates the race test that should catch it. The 2025 commit lost no pet in 50 rounds, so it likely appeared between June 2025 and July 2026, possibly with the move to Spring Boot 4 (INFERRED; not bisected, and one 50-round run each). Upstream added pets through the owner from `c953442` (2022-01-05, "Remove PetRepository and use Owner as aggregate"); before that, `PetController` saved the pet with `pets.save(pet)`. Probing stopped there on Prem's call: the question was whether it existed before the course, and it did.

## Why it was not seen

The race test was in the repository before the course started: Week 1's generated `CLAUDE.md` lists `PetClinicConcurrencyTests`, and `baseline/README.md` records it as upstream's. Week 2 did not add or change it.

the existing race test `testDuplicatePetNameRaceConditionIsBlocked` passed because its first request was slow on a cold start, so the two requests rarely overlapped. The test was right; the timing hid the defect. PC-301's microchip race test, which runs first in the same class, warms the context and exposed it.

## For PC-301

Not fixed in PC-301 (Prem, 1 November): it is outside the change and no decision covers how the controller saves an owner. The race test stays as it is and is not disabled: when it fails, it is detecting this defect. PC-301's triage lists it as a known defect with this ticket.

## Open

- Whether the orphaned pets need finding and reattaching in a real database.
